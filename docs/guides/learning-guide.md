# 이번 변경을 공부하는 순서

## 1. 폴더 이동과 기능 변경을 구분하기

| 이전 위치 | 현재 위치 | 바뀐 이유 |
|---|---|---|
| 루트 Python 설정·테스트·scripts·data | `backend/` 아래 | 서버 실행에 필요한 파일을 한곳에 모음 |
| `backend/main.py`, `backend/api` 등 | `backend/app/main.py`, `backend/app/api` 등 | `backend` 프로젝트 안에서 실제 Python 패키지를 `app`으로 분리 |
| `docs/design.md` | `docs/architecture/original-backend.md` | 원본 에이전트 설계 보존 |
| 과거 구현/검증 문서 | `docs/archive/` | 현재 실행 계약과 과거 기록 혼동 방지 |
| 없음 | `frontend/src/features/` | 기능별 화면·상태·테스트를 가까이 배치 |

모든 파일을 처음부터 다시 만든 것은 아닙니다. 기존 도구와 수식은 이동·import 경로 조정 후 원래 테스트로 확인했습니다. 새 기능은 작업 상태 관리와 사용자 화면에 집중했습니다.

## 2. 버튼에서 서버까지 따라가기

먼저 `frontend/src/features/analysis/AnalysisForm.tsx`를 읽습니다. 입력을 모아 `onSubmit`을 호출할 뿐, 분석 시작 여부는 결정하지 않습니다.

다음 `useAnalysis.ts`에서 브라우저의 **전송 중** 상태와 UUID 생성을 봅니다. `api/client.ts`가 이를 `Idempotency-Key`로 전달합니다. `backend/app/api/routes.py` → `services/jobs.py` → `repositories/jobs.py`가 접수를 저장한 후 202를 반환합니다.

그제야 화면에 **실행 대기 중**이라고 표시합니다. 같은 UUID로 재요청하면 기존 접수를 돌려줍니다. 네트워크가 끊겨도 새로운 작업을 무작정 생성하지 않는 이유입니다.

## 3. 실제 계산이 어디서 시작되는지 보기

`backend/app/services/worker.py` → `services/jobs.py:run_once`에서 작업자가 실행을 맡고 시작 시각을 저장합니다. 이후 `services/analysis.py` → `agents/graph.py` → `tools/`로 계산이 이어집니다.

`repositories/jobs.py`는 화면에 전달할 스냅샷을 저장합니다. 상태 조회가 이 저장소를 별도 연결로 읽기 때문에, 오래 걸리는 기상 조회가 화면의 상태 확인까지 막지 않습니다.

기존에는 POST 요청이 계산 완료까지 기다렸습니다. 지금은 접수와 계산이 분리되어 있습니다. **빠른 202 응답은 빠른 계산 완료를 의미하지 않습니다.**

## 4. 잘못된 승인을 막는 세 겹의 확인

1. 화면: `state.ts`가 확인된 상태와 선택 조건을 검사하고 승인 버튼을 잠급니다.
2. 검토 창: `ApprovalPanel.tsx`가 창을 열 때의 분석 ID와 결과 토큰을 보관합니다. 결과가 바뀌면 다시 검토해야 합니다.
3. 서버: `jobs.py:decide`가 인증 이후 최신 분석·만료·토큰·해결되지 않은 경계·시연 여부를 다시 검사합니다. 브라우저 검사를 우회해도 서버에서 차단합니다.

새 승인을 시작할 때 `decision_intents`와 `jobs.status=decision_pending`을 한 트랜잭션으로 저장합니다. 그 후 프로세스가 중단되어도 화면이 다시 미결정 상태로 돌아가지 않습니다. 동일한 결정만 재시도할 수 있고 확정 기록은 한 번만 남습니다.

## 5. 정확성을 위해 고친 비효율

| 발견한 문제 | 수정 | 결과 |
|---|---|---|
| 계산 잠금 때문에 상태 조회까지 기다림 | 조회용 짧은 DB 연결 | 계산 중에도 상태 확인 가능 |
| 승인 잠금을 잡고 긴 계산을 기다림 | 계산 잠금 최대 250ms, 확보 후 검증 | 다른 접수가 오래 막히지 않고 만료된 승인도 차단 |
| 탭 복귀 때 조회가 겹침 | 진행 중 조회 하나, 가시성 세대 검사 | 중복 요청과 오래된 응답 덮어쓰기 방지 |
| 안 보는 탭에서도 계속 요청 | 숨김 시 중지, 복귀 시 재확인 | 불필요한 호출 감소 |
| 처음부터 차트 코드 로드 | 결과가 있을 때 동적 import | 빈 화면의 초기 로드 비용 감소 |
| 일시적인 DB 오류로 작업자 종료 | 재시도·오류 상태·readiness 확인 | 영구적인 큐 정지 방지 |

프론트엔드 조회가 가벼워졌다고 계산 모델이 빨라지거나 정확해진 것은 아닙니다. 응답 시간과 모델 정확도는 각각 측정해야 합니다.

## 6. 테스트로 실패 상황 공부하기

- `backend/tests/test_jobs.py`: 접수/실행 구분, 중복 요청, 생존 신호 만료, 결과 만료, 오래된 결과 승인 차단, 프로세스 중단, DB 장애 재시도.
- `backend/tests/test_recovery.py`: 그래프 체크포인트와 감사 기록 저장 사이의 장애 및 재시도.
- `frontend/src/features/analysis/useAnalysis.test.tsx`: 응답 유실, 이전 요청의 늦은 응답, 탭 복귀 시 경쟁 상태.
- `frontend/src/features/approval/ApprovalPanel.test.tsx`: 검토 중 결과가 바뀌어도 새 결과를 무심코 승인하지 않는지.
- `frontend/tests/console.spec.ts`: 실제 화면에서 분석부터 시연 승인까지, 통신 단절, 인증 실패, 모바일, 키보드, 접근성.

테스트의 `Event`, 지연된 Promise, 브라우저 요청 가로채기는 장애를 의도적으로 만들어 검증하기 위한 장치입니다. 실제 데이터 정확도를 검증하는 실험과 구분해야 합니다.

## 7. 아직 남은 모델 과제

현재 시연은 고정된 24시간 값입니다. 기존 회귀 학습 스크립트는 기상·설비 특성에서 같은 시간의 발전량으로 회귀합니다. 사용자가 의도한 **전날까지의 관측으로 다음날 24시간 발전량 예측**을 만들려면 예측 기준 시각, 사용할 관측 이력, 다음날 타깃 정렬, 시차/이동 통계 특성, 시간순 백테스트, 누락 처리와 오차 평가가 추가로 필요합니다. 이번 UI·상태 개선으로 이 모델이 완성됐다고 볼 수 없습니다.

스타일도 책임별로 나눴습니다. `styles/base.css`는 기본 태그·접근성, `layout.css`는 메뉴와 페이지 배치, `components.css`는 공통 입력/버튼/모달, `responsive.css`는 화면 크기 대응입니다. 차트·배분·승인 스타일은 각 `features/` 폴더의 CSS에서 수정합니다.
