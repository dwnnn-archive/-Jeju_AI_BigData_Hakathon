# 당일 점검 (초단기예보) — 시험 브랜치 `안봄-초단기예보`

하루 전 계획(단기예보)이 "정상"인 날만 당일에 초단기실황·초단기예보로 다시 점검하는 기능이다. 하루 전 판정이 위험이면 거기서 끝내므로 **놓침만 줄이는 구조**다. 근거는 [pipeline-evaluation.md](pipeline-evaluation.md)의 시뮬레이션(포착 81~83% → 약 93%, 오경보 +14~39일).

이 브랜치는 `안봄` 위에서 실험하는 시험 브랜치다. 기술 검증이 끝나지 않거나 팀이 당일 점검을 하지 않기로 하면 브랜치만 지우면 된다.

## 성공 기준 (기술 검증)

| 기준 | 상태 |
|---|---|
| 1. 실제 키로 초단기 API 호출, 풍속·기온·하늘상태 파싱 | **완료** |
| 2. 실측·초단기예보·하루 전 예보를 이어 붙인 입력으로 판정이 동작 | **완료** |
| 3. 당일 점검 결과를 이력으로 남기고 화면에 표시 | **완료** (작업 이력에 단계·회차 저장, 이력 표와 요약에 표시) |
| 4. 서비스 흐름(작업 큐, 그래프, 승인)에 연결 | **완료** (아래 "서비스 규칙") |
| 5. 실제 서버 구성으로 처음부터 끝까지 | **완료** (실제 기상청 호출과 실제 모델로 확인, 아래) |
| 실제 정확도 이득 | **지금은 측정 불가.** 예보 저장 장치가 이력을 쌓아야 확인된다 ([forecast-archive.md](forecast-archive.md)) |

## 확인한 사실 (가이드 + 실제 호출)

- 초단기실황(`getUltraSrtNcst`)은 매시 정각 자료(10분 뒤부터), 풍속 `WSD`·기온 `T1H`가 있고 **하늘상태는 없다.** 현재 정시 한 시점뿐이라 같은 날 지난 시간의 실측 이력은 이 API로 얻을 수 없다.
- 초단기예보(`getUltraSrtFcst`)는 매시 30분 생성, 45분 뒤부터 제공, **기준 시각의 다음 정시부터 6시간**이다(기준 20:30 → 21:00~02:00). 시각은 단기예보처럼 `fcstTime HH00 → HH시`로 읽는다.
- **초단기예보의 풍속·기온은 정수로 온다**(`WSD 3, 4, 5`). 단기예보보다 거칠다.
- 같은 키·같은 주소(공공데이터포털)로 단기예보와 함께 동작한다.
- **기상청은 최근 3일 치 발표분만 다시 준다**(`최근 3일 간의 자료만 제공합니다`). 그래서 당일 점검의 하루 전 입력은 전날 23시 발표분을 그때그때 다시 받아 쓰면 되지만(저장 불필요), **예보 정확도를 평가하려면 예보를 저장해 두는 것이 유일한 방법**이다.

## 동작

`ToolBundle.intraday_check(request, now)` (`app/tools/bundle.py`)

1. 하루 전 입력: 전날 23시 발표 단기예보를 다시 받는다(고산 격자는 발전량 모델용, 제주시 격자는 수요 모델용).
2. 초단기실황과 초단기예보를 두 격자에서 받는다.
3. `blend_weather`(`app/tools/intraday.py`)로 하루 24시간을 이어 붙인다.

| 시간 | 쓰는 값 |
|---|---|
| 점검 시각 이전 | 하루 전 예보 (이미 지난 시간, 판정에서도 제외) |
| 점검 시각(현재 정시) | 초단기실황의 풍속·기온, 하늘상태는 초단기예보 또는 하루 전 예보 |
| 이후 6시간 | 초단기예보 (풍속·기온·하늘상태) |
| 그 뒤 | 하루 전 예보 |

4. 발전량 모델과 수요 모델로 예측하고 `rules.evaluate(..., from_hour=지금 시각)`로 판정한다. **지금 시각 이후**의 시간만 피크와 등급에 쓴다. 표에는 24시간이 모두 남는다.

모델·키·입력이 하나라도 없으면 시연값 등으로 조용히 대체하지 않고 예외를 낸다. 반환값의 `inputs`(하루 전 발표분, 시간별 출처, 이어 붙인 날씨)는 나중에 저장해서 정확도 평가에 쓰도록 남긴 것이다.

## 서비스 규칙 (서버가 강제한다)

요청에 `phase: "intraday"`를 넣어 보내면 기존 작업 큐·그래프·승인 흐름을 그대로 쓴다(`POST /api/v1/analyses`). 아래 조건이 어긋나면 접수하지 않는다.

| 조건 | 어기면 |
|---|---|
| 대상 날짜가 **오늘(KST)** | 422 |
| 같은 날짜·지역·모드의 하루 전 분석이 있다 | 409 |
| 진행 중인(대기·실행) 작업이 없다 | 409 |
| 직전 **성공한** 결과가 하루 전 또는 이전 점검의 **정상(NORMAL)** | 409 (위험이 나온 날은 승인 대기를 밀어내지 않는다) |
| 당일 점검 횟수가 최대(기본 2회, `MAX_INTRADAY_CHECKS`) 미만 | 409 |

- **실패·중단된 시도는 건너뛴다.** 기상청 장애로 07:45 점검이 실패해도 10:45 점검이 가능하고, 실패는 횟수에 들어가지 않는다.
- 같은 멱등 키의 재요청은 기존 접수를 돌려준다. 스케줄러용 명령은 같은 날짜·슬롯에 항상 같은 키를 보낸다.
- 하루 전이 정상으로 끝나면 그래프가 거기서 끝나고, 점검이 위험을 내면 하루 전 위험과 똑같이 배분 → 통보문 초안 → 담당자 승인 대기로 간다. 실제(live) 모드는 검증 전이라 승인·발송이 계속 막혀 있다(`operational_validation_missing`).
- 시연(demo) 모드에서는 시나리오 `intraday_escalation`(하루 전 정상, 당일 1차 정상, 2차 위험)으로 전체 흐름을 볼 수 있다.

## 실행

```bash
# 서버가 떠 있는 상태에서, 외부 스케줄러가 정해진 시각에 호출한다
python -m scripts.run_intraday --slot 0745     # 07:45 점검
python -m scripts.run_intraday --slot 1045     # 10:45 점검
```

종료 코드 0은 정상, 10은 위험(승인 대기), 1은 요청 실패나 규칙 위반, 2는 시간 초과다. 예보 이력을 쌓는 정기 수집은 `python -m scripts.forecast_archive collect`다([forecast-archive.md](forecast-archive.md)). 필요한 설정: `JEJU_MODEL_DIR`, `JEJU_DEMAND_MODEL_DIR`, `KMA_API_KEY`(live 모드).

## 처음부터 끝까지 확인 (2026-11-16 22:09, 실제 호출)

임시 DB, 실제 단기·초단기 예보, 실제 학습 모델로 확인했다.

1. **하루 전(내일, 실제)**: 완료, NORMAL(최대 비율 0.208). 출처는 기상청 · 예측 모델 · 수요 모델이고 승인은 `operational_validation_missing`으로 막힌다.
2. 오늘 날짜의 하루 전 분석이 없어(어제 돌린 적이 없다) **임시 DB에만 "하루 전 정상" 기록을 심었다.**
3. **당일 점검 1차**: 어젯밤 23시 발표분을 다시 받아 하루 전 입력으로 쓰고, 실황 1시간·초단기예보 2시간을 덧씌웠다(시간별 출처 하루 전 21 · 실황 1 · 초단기 2). NORMAL, `from_hour` 22.
4. **2차**: 같은 방식으로 NORMAL. **3차는 409**(`limit has been reached`).
5. 이력에 `day_ahead` / `intraday` 단계와 회차가 구분되어 내려온다.
6. **예보 저장 장치**: 발표 8건(단기 4, 초단기예보 2, 실황 2), 값 4,140행, 판정 기록 3건. 단기예보 14개·초단기예보 11개·실황 8개 항목이 모두 저장됐고, 당일 점검 2회가 같은 발표를 써서 중복 저장되지 않았다.

한계: 점검 시각이 밤이라 시간별 출처가 적고(22시 이후 2시간), 낮 시간대의 위험 판정은 아직 시험하지 못했다. 밤 시간대 값은 상식적이었다.

## 한계와 다음 단계

- **정해진 시각에 자동 실행하는 장치는 만들지 않았다.** `run_intraday`와 `forecast_archive collect`를 외부 스케줄러(작업 스케줄러, cron 등)가 호출하는 방식이다. 앱 내부 스케줄러로 할지는 팀 결정이 필요하다.
- **화면에 "당일 점검 요청" 버튼은 없다.** 화면은 단계와 회차를 보여 주기만 한다(이력 표 "단계" 열, 요약 "판정 단계").
- 점검 시각(07:45, 10:45)은 출력제한 피크(9~15시) 3~6시간 전이다. 그 시간에 담당자 승인과 설비 대응이 가능한지는 확인하지 못했다.
- 시뮬레이션의 93%는 초단기예보 오차를 가정한 값이다. 실제 이득은 예보를 쌓은 뒤에야 확인된다.
- 초단기예보는 정수라 풍속·기온이 거칠다. 같은 날 지난 시간의 실측 이력은 이 API로 얻을 수 없다.
- 하루 전 단계의 오경보는 줄지 않는다(위험으로 본 날은 다시 확인하지 않는다).
